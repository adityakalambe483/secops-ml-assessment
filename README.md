# SecOps-ML: ML-based security log analysis, alert correlation & compliance mapping

Prototype for the *AI/ML Developer Intern* technical assessment. Pipeline:

```
logs (CSV/JSON/API) ─► validation ─► feature engineering ─► ML detector ─► alerts
        ─► correlation engine ─► incidents (+ threat-intel enrichment)
        ─► compliance mapping (NIST CSF 2.0 / ISO 27001:2022) ─► report (HTML/MD/JSON) + REST API
```

## Quick start (Windows PowerShell / VS Code terminal)
```powershell
cd secops-assessment
Set-ExecutionPolicy -Scope Process Bypass      # only if script activation is blocked
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
$env:PYTHONUTF8="1"                            # optional, avoids encoding issues on Windows
$env:PYTHONPATH="src"
python -m secops.cli all                       # generate data -> train -> analyse -> reports/ (~1-2 min)
python -m pytest -q tests                      # expect: 15 passed
start reports\security_report.html             # open the report in the browser
python demo_compare.py                         # normal vs attack events, features + model score
python -m secops.cli serve                     # API -> open http://127.0.0.1:8000/docs
```
**macOS / Linux:** `python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt && export PYTHONPATH=src`, then the same `python -m secops.cli ...` commands.
Note: `PYTHONPATH` must be set again in every new terminal. Stop the API with `Ctrl+C`.

### API
| Endpoint | Purpose |
|---|---|
| `GET /health` | liveness + model status |
| `POST /analyze` | JSON events → alerts, incidents, findings |
| `POST /analyze/upload` | CSV / JSON / JSONL file upload |
| `GET /analyze/sample` | analyse the bundled hold-out logs |
| `POST /report?format=html|md` | formatted report |
| `GET /threat-intel/{ip}` | IP reputation lookup |

Required event fields: `timestamp, src_ip, dst_asset, dst_port, event_type, user, bytes_out, status` (`severity` optional).
Validation: IP syntax, known event types/status, port range, non-negative bytes, parseable timestamps, ≤50,000 events,
25 MB upload cap. Errors → HTTP 422 (schema/content), 400 (empty upload), 413, 503 (model missing).

```bash
curl -s localhost:8000/analyze -H 'content-type: application/json' -d '{"events":[{"timestamp":"2026-09-20T02:00:00",
 "src_ip":"203.0.113.9","dst_asset":"web-01","dst_port":22,"event_type":"login_failed","user":"root","bytes_out":0,"status":"failure"}]}'
```

## Task 1 – Dataset & model
**Data source:** *synthetic*, generated by `datagen.py` (seed 42): 21 days, **35,667 events, 4,930 attack events (13.8%)**,
70 ground-truth incidents of six types (brute force, recon scan, SQL-injection, multi-stage attack chain, malware + C2 beaconing,
insider exfiltration). Attacker IPs use RFC 5737 documentation ranges. Benign traffic deliberately contains **hard negatives**:
typo'd passwords, internet background firewall denies, nightly 5 GB backup, authorised weekly vulnerability scanner (10.0.50.5),
admin `sudo`, legitimate account creation, big legit file copies, AV false alarms. Labels come from the generator (no manual labelling).

**Features (33):** hour/off-hours/weekend, port, log-bytes, status, internal-source, privileged-user, event-type one-hot, tool severity, and
trailing 5-minute window counts per source / asset (events, failed logins, deny events, distinct ports, distinct assets, bytes, same-type events)
plus inter-arrival mean and coefficient of variation (beaconing). Windows look backward only (no future leakage).

**Evaluation protocol:** temporal split – first 14 days train (1–14 Sep), last 7 days test (15–21 Sep) (`models/metrics.json`). Model selection and the alert
threshold are chosen by 5-fold out-of-fold predictions on the *training* set only.

| Model (5-fold CV on train) | PR-AUC | F1 @ best thr |
|---|---|---|
| Logistic regression | 0.9936 | 0.9707 |
| **Random forest (selected)** | **0.9999** | 0.9968 |
| Hist. gradient boosting | 0.9997 | 0.9985 |

**Hold-out test (12,145 events):** precision 0.998, recall 0.997, F1 0.998, ROC-AUC 1.000, PR-AUC 0.9999.
Confusion matrix: TN 10,216 · **FP 4** · **FN 5** · TP 1,920.
Baseline "alert if the source tool's severity ≥ medium": precision 0.61, recall 0.18, F1 0.28 – the ML model is far better than the tool severity.
Ablation without event-type/severity features (behaviour only): F1 0.998 → the model is not just reading signature-like event types.

**False positives (4):** 2 AV `malware_detected` PUA alarms on workstations, 1 file_access, 1 web_request – i.e. the genuinely ambiguous
benign events. (When analysing the hold-out file alone, 2 alerts from the authorised scanner 10.0.50.5 also appear, because features lose the
earlier training-period context.) **False negatives (5):** 4 file_access events at the start of insider bulk-access bursts and 1 firewall_deny at the start of a scan –
the first events of a burst look normal until the window fills. Per-attack recall is 99–100% for every type (see `metrics.json`).

### ⚠ Read this before trusting the numbers
The near-perfect scores come from **synthetic data whose attacks are cleaner than real traffic** (generator-defined patterns, attackers from
distinct IP ranges, off-hours bias – `src_internal`, `dst_port` and `hour` are the top permutation-importance features, which partly reflects
generator artefacts). They demonstrate that the pipeline is correct and leak-free, **not** that it would reach 99.8% F1 in production. Real
logs (CICIDS2017, UNSW-NB15, Boss of the SOC, own SIEM exports) would need re-training, would produce more false positives, and would need
analyst feedback loops. Other limitations: supervised model only detects patterns similar to the six simulated attack types (no novel-attack
detection – an Isolation-Forest layer would be the next step); first events of a burst are missed; authorised scanners/backups need an
allow-list in production; 5-minute windows miss low-and-slow attacks; no streaming ingestion.

## Task 2 – Alert correlation (`correlate.py`)
Alerts (probability ≥ threshold) are linked with union-find using three rules: **R1** same source IP ≤15 min; **R2** same target asset ≤5 min from
different external sources (distributed attacks); **R3** *pivot* – an asset that was attacked later appears as a source (≤60 min), which links
"attacker → web-01" with "web-01 → external exfiltration". Each incident gets kill-chain stages, severity (max category risk, +1 for two stages, critical for ≥3
stages, +1 for high-confidence threat-intel hit), a mean model probability, **human-readable reasoning** built from measured facts (counts, windows, distinct ports/accounts,
MB transferred, inter-arrival CV) and the top-5 supporting events (with event ids so they can be traced to raw logs).

**Verified against ground truth** (hold-out): 24 true incidents → 100% recovered in a single cluster, 0 split, 0 missed; every cluster containing attacks has purity 1.0;
5 additional low/medium-severity clusters are pure false positives (AV alarms, authorised scanner).

## Task 3 – Compliance mapping
Each incident is split into findings per category with: control references (**NIST CSF 2.0** and **ISO/IEC 27001:2022 Annex A**), MITRE ATT&CK tactic/technique,
evidence, risk level (category base risk, +1 in multi-stage chains / threat-intel hit, −1 for weak evidence), and prioritised remediation steps (`knowledge.py`).
Control mappings are my reading of the standards – verify against the official texts before relying on them in an audit.

## Task 4 – Connectors & backend
`FileLogConnector` (CSV/JSON/JSONL, schema validation) and `ThreatIntelConnector` (local feed + optional AbuseIPDB; private IPs are never sent out; timeouts/failures
are caught and noted, never crash the pipeline). The feed shipped here is **synthetic** and intentionally covers only ~60% of attacker IPs, so the model does not depend on it.

## Task 5 – Report
`reports/security_report.html` (open in a browser) and `.md`: executive summary, model performance, incidents with reasoning + evidence, compliance-mapped findings with remediation.
Regenerate with `python -m secops.cli analyze`.

1. `python -m secops.cli all` → show metrics, FP/FN analysis. 2. Open `reports/security_report.html` → walk through the Critical multi-stage incident (recon → brute-force → priv-esc → new account → exfiltration).
3. `serve` → `/docs` → `GET /analyze/sample`, then POST a small custom brute-force payload and a malformed one (422). 4. Explain one detection from raw events → features → probability → incident → control.
